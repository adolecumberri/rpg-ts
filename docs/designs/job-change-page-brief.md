# Job Change Page (Oficio)- **Author:** Lead (EGM brainstorm, DSH)- **Date:** 2026-11-02## OverviewThe Oficio panel in the Team page answers "what does this job change cost meand what does it give me?" Today it only lists jobs and stat deltas. Theplayer cannot see the target job's four skills, cannot tell which skills theyalready know, and the currently held job was only blocked at the confirmbutton.The change makes the page a preview: the target job's whole skill ladder onscreen, unknown skill names masked as `????`, the already-held jobunselectable, and the stat block shown as **Before → Change → After**.## Analysis- The player's knowledge must survive characters leaving the party: it is a  **player-level memory**, persisted like the place flags (`knownSkills` on the  save), not derived per character.- The job page shows the **job definition's ladder** (`progression.skills`),  never `ownedJobSkills`: ownership decides who can cast a skill in combat;  knowledge decides whether the page reveals the name.- A recruit that arrives already trained (a `soldier_2` spawn at job level 3)  must backfill the memory: `syncKnownSkills()` runs on recruit/job change,  after reward xp, on load and when the page opens.- The stat columns must agree with each other: `Before` is the live value,  `Change = After − Before`, `After = Before − oldJobBonus + newJobBonus`.## Goals vs Non-Goals- **In scope:** job ladder with levels; `????` masking; current job disabled;  Before/Change/After table; persisted known-skill memory (backfilled).- **Out of scope:** the skills catalog redesign (one skill with three levels)  — designed in `combat-and-stats.md`, not implemented in this change.## Alternatives Weighed- *Derive knowledge from the party on every page load* — rejected: a character  that dies or leaves would erase names the player already saw.- *Hide unknown skills entirely* — rejected: the player should know a skill  exists at level 3/5, just not its name.- *Three separate skills per rank (disarm/disarm_2/disarm_3)* — the direction  chosen for the catalog redesign is one skill with a level; the page groups  the ranks under one row already.## Key Decisions & Staging1. `WorldSession.knownSkillIds` (persisted `knownSkills`), `knowsSkill()`,   `syncKnownSkills()`; called from `setJob`, reward settlement, save load   and the job-page open.2. `jobSkillRows()` renders `progression.skills` with name masking.3. `jobCompareRows()` renders the three columns.4. Dev roguelite flow (`screens/dev/RogueliteScreen.tsx`) exercises the loop:   team creation, escalating waves, weapon rewards — implemented and verified.5. Skills model redesign (one skill, 3-value arrays indexed by level,   description functions) is captured in `combat-and-stats.md` as the next   implementation stage.
